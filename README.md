## How To Use

Just get the .uf2 image from the latest release and flash it on your Pico by
powering it up while holding the white BOOTSEL button and copy the .uf2 image to
the RPI-RP2 device that should appear on your storage devices. After that,
you're good to go! You don't really need to do anything, it should start up
after a second and a half. One feature I added is muting. By pressing the
picobricks button you can toggle audio. The LED next to the button lights up
when audio is muted.

## Building

### This section assumes you're using Linux or any other Unix-like OS, since using development tools are much more straightforward with the command line

To prepare the audio and video files, which are just text files including C
arrays containing data, run their respective python scripts and redirect the
output to their respective files.
You need the python packages `mido` and `opencv-python` to process MIDI and
video to prepare the data files. They can be install with pip.
To build the firmware image, you need a C compiler for the Pico's architecture,
the Pico SDK and CMake installed on your system. Make a build directory and go
into it. Initialize CMake by running `cmake ..` and
after that you can build by running `make`. If everything goes successfully, you
should have a file named `badapple.uf2` which is the firmware image you can
flash on the Pico by powering it up while holding the
white "BOOTSEL" button, putting it into the USB bootloader mode. The Pico will
appear as a storage device named `RPI-RP2`. Copy the .uf2 file over to the
virtual `RPI-RP2` storage device and your picobricks should
be ready to play Bad Apple!!

## It didn't work

Your picobricks parts are most likely wired up differently compared to what I
have. In that case, you need to change the GPIO pin definitons at the start of
the .c source code file and build by yourself. By default (A.K.A. on my
picobricks) the buzzer is GPIO 20, the LED is 7, the button is 10 and the OLED
i2c SDA and SCL are 4 and 5 respectively.

## How does it work under the hood?

### Audio

I manually trimmed down the [MIDI file](https://onlinesequencer.net/4140941#) I
found from onlinesequencer.net so it only had one note playing at a time, due to
how the piezoelectric buzzer works. I also set the BPM to 138, it is 137 by
default and causes time drift.I plan to make it more detailed, since the
start of the song sounds too plain compared to
the original song. The python script `audiogenerator.py` then later parses the
MIDI file and outputs the events as a C array of Note structs. The structure
contains the frequency (Hz), duration (microseconds). The text file containing the C array of the note data
named `audio.txt` is included in the source code (In C, `#include` just tells
the preprocessor to paste a text file before compilation and further processing.
It doesn't necessarily have to be a .h header file.). In the C code, audio is
processed in the second core since I thought processing both audio and video on
a single core could have implications, although less with hardware PWM. The
second core iterates over the notes[] array and processes each note by
controlling the PWM hardware, which allows the Pico to generate accurate and
precise square waves that don't cause a software overhead. The PWM signal then
drives the buzzer. For more details, you can read [this article by
I-Programmer](https://www.i-programmer.info/programming/hardware/14849-the-pico-in-c-basic-pwm.html).
It was an helpful resource for me to understand how PWM worked while building
this project.

### Video

The video is more interesting, since I used some techniques to compress the
frames to fit the 2 MiB flash of the Pico. The raw uncompressed frame buffers,
1024 bytes each, would take over 6 megabytes of space even with the 128x64
resolution, so some compression is necessary. In the python script
`framebuffergenerator.py` the video `badapple.webm` (which is already 128x64, I
processed it with ffmpeg) is processed frame by frame. The frame is first turned
into grayscale, and then turned into boolean ones or zeros using a threshold of
127. However, the hardcoded threshold of 127 doesn't yield great results in the
frames where there is a flame, which is made up of the shades of gray. I may try
other thresholds such as Otsu and try if they look better. Anyway, after turning
the frame into boolean ones and zeroes, an XOR operation is applied between the
current frame and the frame before. This results the difference of the two
frames, which is easier to compress. After this, the 2-dimensional numpy array
that represents the XOR difference between the current and last frame is
flattened into a single dimension, starting from the top-left corner and going
down and wrapping to the top of the next column, since this is closer to how the
OLED controller expects the bytes. Furthermore, the flattened XOR array is
represented by how long a sector bits go. For example, {0, 0, 1, 1, 1, 0, 0, 1}
is represented as {2, 3, 2, 1}. Since there are only two states a bit can be in,
the type of the bit sector doesn't have to be specified, as a new sector means a
bit flip. Only the starting bit is stored in a seperate array for each frame.
This method greatly reduces the size of frames with little change, as the entire
frame can be represented by a dozen of numbers instead of a whole kibibyte. We
have greatly reduced the size of the video at this point. If I remember it
correctly, the number I got while testing while representing each number as a
16-bit unsigned integer was around 2.4 megabytes. As you can see, this is not
compact enough to fit in the 2 MiB of flash of the Pico. As I was looking at the
raw data, I noticed the frames that took the most numbers to represent were
frames that had a lot of change (obviously) and also those numbers were quite
small. Most numbers didn't need 16 bits, they could fit in just 8 bits. The
numbers that took more than 8 bits to represent were mostly for static (or
almost static) frames where the entire frame could be represented by a few big
numbers. The biggest number the current method needed was 8192, since the 128x64
screen has only 8192 pixels and therefore bits. Even 8192 doesn't need all 16
bits, taking only 14 bits which can be further reduced down to 13 by
decrementing each number since a sector of bits with the length of 0 doesn't
make sense. The remaining 3 bits could be used for a special variable-length
encoding that used less data for smaller numbers. I took inspiration from [how
UTF-8 works](https://www.youtube.com/watch?v=MijmeoH9LT4) and implemented my own
method. It works like this: The first bit of a byte is turned on if this is a
number that needs two bytes. That leaves 7 bits for a single byte long number
which 128 and under can be represented using the decrement technique. Anything
greater needs two bytes. If that is the case, the first bit of the two bytes is
flipped on and the number is represented using the remaining 15 bits. Using this
encoding, I was able to get the size down to around 1.3 megabytes which is small
enough to fit on the Pico's flash. In the `framedata.txt` file, the numbers that
represent each frame are concatenated into one single array and each frame's
data is distinguished by a seperate array that keeps how many numbers (yes
numbers, not bytes. the for loop in the C code skips a byte when it encounters a
two byte number) a frame is made out of. The three mentioned arrays which are
the frame data, frame sizes and starting bits are stored in the file
`framedata.txt` and included in the source code. In the C code, the steps of
compression that were went over in this section are reversed frame by frame to
build a framebuffer. Before the framebuffer can be sent to the display, the
bytes have to be reordered since the SSD1306 uses a page-based byte ordering
system (at least by default) more suitable for text. The SSD1306 OLED controller
splits the display into eight pages (kind of like a page of a notebook), each 8
pixels high and 128 pixels wide. Each byte represents a one pixel wide slice of
a page (most significant bit on the top of the slice), from left to right and
top to bottom. After reordering the bytes according to how the SSD1306 orders
them, the framebuffer can be finally sent.
